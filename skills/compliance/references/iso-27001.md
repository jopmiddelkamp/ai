# ISO 27001 Engineering Rules

ISO/IEC 27001:2022 is the international standard for information security management (ISMS), with 93 Annex A controls across organizational, people, physical, and technological themes. Certification is voluntary and audit-based, not a legal requirement. Enterprise customers often demand it, and an auditor looks at your history, so a project that may pursue it applies these rules while writing code; no control is "added later".

## Secure development (A.8.25–A.8.34)

- Treat every feature that touches sensitive data or takes automated actions as security-relevant, and state its security requirements in the PR or spec before coding (A.8.26).
- Follow secure coding practice: validate and type all input at API boundaries, use parameterized queries only, encode output, never build SQL, shell, or prompt strings by concatenation (A.8.28).
- Keep development, test, and production fully separated: separate environments, credentials, databases, and third-party API keys (sandbox keys outside prod) (A.8.31).
- Never use production data in tests or local dev; generate synthetic data instead (A.8.33).
- Ship every change through a reviewed pull request with CI running tests, linting, dependency audit, and secret scanning; no direct pushes to the main branch (A.8.32, A.8.29).
- Pin dependencies with a lockfile, run automated vulnerability scanning (for example Dependabot or osv-scanner) in CI, and patch critical CVEs before other work (A.8.8).
- If infrastructure is defined as code, give it hardened defaults (deny-by-default network rules, no public buckets, TLS-only) and treat IaC changes like code changes (A.8.9, A.8.27).
- Restrict repository access and branch permissions; the repo is the source-code access control (A.8.4).
- Never commit secrets; load them from the environment or a secret manager, keep `.env` gitignored, and add a pre-commit secret scan (A.8.28).

## Access control & authentication (A.5.15–A.5.18, A.8.2–A.8.5)

- Enforce deny-by-default authorization on every backend endpoint: a user reaches only data they are entitled to, checked server-side per request, never trusted from the client (A.5.15, A.8.3).
- Model the project's roles explicitly and grant least privilege per role; external parties get scoped, revocable access only (and, if the app is multi-tenant, tenant-specific access) (A.5.18).
- Require strong authentication: MFA on admin surfaces (and on user accounts where the risk warrants it), short-lived access tokens with refresh rotation, and generic error messages that do not leak account existence (A.8.5).
- Give every user, service, and integration its own identity; no shared accounts, no shared API keys between integrations (A.5.16).
- Hash passwords with argon2id or bcrypt; never log, email, or store credentials or tokens in plaintext anywhere, including crash reports (A.5.17).
- Put admin and support functionality behind a separate privileged role with MFA, and log every use of it (A.8.2, A.8.18).
- Build deprovisioning as a first-class feature: revoking a user's access takes effect immediately across every surface (API, web, mobile, offline sync where present) (A.5.18).

## Cryptography & data protection (A.8.24, A.8.11, A.8.12, A.5.14)

- Enforce TLS 1.2+ for all transport (API, webhooks, integration calls) and reject plain HTTP; if there is a mobile app, enable certificate pinning or strict certificate validation (A.8.24, A.5.14).
- Encrypt all data at rest: databases, backups, object storage, and any sensitive data stored on devices (A.8.24).
- If there is a mobile app, store tokens and keys only in the platform keystore (iOS Keychain, Android Keystore), never in shared preferences or plain files (A.8.24).
- Use vetted crypto libraries and platform primitives only; never implement custom crypto, and keep keys in a managed KMS or secret manager with rotation support (A.8.24).
- Mask or omit sensitive fields (health or financial details, phone numbers, addresses) in logs, error messages, analytics events, and LLM or automation prompts (A.8.11, A.8.12).
- Classify data in code: mark sensitive records and personal contact data as sensitive in the data model, so serializers, loggers, and exports can treat them differently (A.5.12, A.5.34).

## Logging & monitoring (A.8.15–A.8.17)

- Emit structured audit logs for every security-relevant event: login, failed login, permission change, data export, admin action, and, where they exist, sync-conflict resolutions and automated actions (A.8.15).
- Make audit logs append-only and tamper-evident (no update or delete API on audit records), retained separately from application logs (A.8.15, A.5.33).
- Include who, what, when, from where, and on whose behalf in each audit record, using UTC timestamps from NTP-synced servers (A.8.17).
- Add alerting for anomalies from day 1: repeated auth failures, unusual export volume, integration error spikes, and automated-action failures (A.8.16).
- Never log request bodies containing credentials, tokens, sensitive records, or personal data; log identifiers and hashes instead (A.8.15, A.8.12).

## Data lifecycle & backup (A.8.13, A.8.14, A.8.10, A.5.33, A.5.34)

- Implement automated, encrypted, versioned backups of all databases with a tested restore path; keep a restore-test script in the repo and run it on a schedule (A.8.13).
- Store backups in a separate account or region from production, so one compromised credential cannot destroy both (A.8.13, A.8.14).
- Build hard deletion: when a user deletes data or leaves, purge it from the database, search indexes, object storage, client caches, and (by expiry) backups, and record the deletion in the audit log (A.8.10).
- If clients sync data offline, propagate deletions and permission revocations to devices, and wipe device-local data on logout or unenrollment (A.8.10, A.5.11).
- Where a law or regulation sets a retention period for a record type, keep those records retrievable and immutable for that period before any deletion logic applies (A.5.31, A.5.33).
- Define RPO/RTO targets in a continuity doc (for example `docs/security/continuity.md`) and make infrastructure choices (replication, multi-AZ) that meet them (A.5.29, A.5.30).

## Third-party & supplier integrations (A.5.19–A.5.23)

- Before wiring any third-party API (payments, telephony, email, AI, partner systems), record it in the supplier register with data shared, auth method, and DPA or security-terms status (A.5.19, A.5.20).
- Send each integration only the minimum fields it needs; never forward full records to providers that only need a subset (A.5.14, A.5.19).
- Verify inbound webhooks cryptographically (signature or HMAC plus timestamp) and treat all third-party responses as untrusted input (A.5.21, A.8.28).
- Isolate each integration behind its own module with its own credentials, timeouts, retries, and circuit breaker, so one compromised or failing supplier cannot cascade (A.5.22, A.8.27).
- Choose the processing region per supplier deliberately (for example EU-region for personal data under GDPR) and record it (A.5.23, A.5.34).

## Automated actions on a user's behalf (if the system takes them)

Applies when the system places orders, makes payments, calls, emails, or books on a user's behalf.

- Require explicit, revocable, per-action-type consent stored server-side before any automated action, and check it at execution time, not at scheduling time (A.5.15, A.5.34).
- Make every automated action idempotent with a unique action ID, an amount or scope limit where money is involved, and a full audit trail of trigger, content, target, and result (A.8.15).
- Add a kill switch: one flag globally (and per tenant if multi-tenant) that halts all automated outbound actions immediately (A.5.29, A.8.16).
- Require human confirmation for irreversible or high-value actions until an explicit, recorded risk decision says otherwise (A.5.3).

## Incident readiness (A.5.24–A.5.28, A.6.8)

- Maintain an incident-response doc with detection sources, severity levels, containment steps (token revocation, kill switch, credential rotation), and the breach-notification steps that apply (for example 72 hours to the supervisory authority under GDPR) (A.5.24, A.5.26, A.5.34).
- Build incident hooks into the code: feature flags to disable subsystems, forced logout or token revocation endpoints, and integration disable switches (A.5.26).
- Preserve evidence on incidents: never rotate or truncate logs during an investigation, and export relevant audit records before remediation (A.5.28).
- After any incident or near miss, write a post-mortem and turn each root cause into a test, lint rule, or written rule (A.5.27).

## Documentation for audit evidence (A.5.1, A.5.37, A.7.x via hosting provider)

Use the project's existing location for these documents; `docs/security/` is a suggested default.

- Maintain a lightweight risk register; add an entry whenever a design decision accepts a security trade-off (ISMS clause 6.1).
- Keep an asset and data inventory listing systems, data categories, and locations, updated when new stores or integrations are added (A.5.9).
- Document operational procedures (deploy, restore, key rotation, access review) as runnable scripts or step lists in the repo, not tribal knowledge (A.5.37).
- Rely on ISO 27001-certified cloud providers for physical security and record their certifications in the supplier register instead of building physical controls (A.7.x via A.5.23).
- Record quarterly access reviews (who has access to prod, repo, and admin) as dated notes (A.5.18).
